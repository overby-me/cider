# xnu-rpc-free mode: design and incremental plan

Status: design (2026-08-27). Grounded in the #11 perf investigation (docs/plan-aarch64.md
Passes 118-120) and a read of the guest Mach-trap layer. No code landed yet.

## Goal

Let guest processes run with far fewer (ideally zero) synchronous RPC round-trips to
ciderd for XNU/Mach operations. One mechanism serves two ends:

- Performance: one warm `cider exec true` makes ~55 guest<->ciderd round-trips, each its
  own epoll wakeup with no batching, and that is essentially the ~21ms that dominates a
  40ms warm spawn (Pass 118 decomposition: ~14ms host launcher + ~5ms guest dyld + ~21ms
  Mach RPC; Pass 120 round-trip count).
- Architecture: a guest that owns its own XNU state depends less on the daemon, which is a
  stated end-goal in its own right (an "xnu-rpc-free mode").

## How guest Mach ops reach ciderd today

Guest Mach traps are implemented client-side in libsystem_kernel:
`vendor/src/xnu/darling/src/libsystem_kernel/emulation/src/xnu_syscall/mach/impl/mach_traps.c`.
Each `*_impl` calls a `dserver_rpc_*` wrapper (generated by
`vendor/pins/ciderd/scripts/generate-rpc-wrappers.py`) that marshals the call over a
per-thread unix socket to ciderd and blocks for the reply. That send-and-block IS the
round-trip. ciderd receives on an epoll loop and dispatches in
`src/linux/server/src/rpc_wire.rs::dispatch` -> `handler.rs`; call numbers live in
`rpc_wire.rs::callnum`.

## What is ALREADY served in-guest (the precedent to extend)

mach_traps.c already short-circuits self-targeted VM ops to plain Linux syscalls instead of
RPC, when `target == mach_task_self()`:

- `_kernelrpc_mach_vm_allocate/map_trap_impl` -> `mmap` (mach_traps.c ~line 235/339)
- `_kernelrpc_mach_vm_deallocate_trap_impl` -> `munmap` (~273)
- `_kernelrpc_mach_vm_protect_trap_impl` -> `mprotect` (~303)

And the self-ports are cached once per process in libsyscall's `mach_init_doit`
(`vendor/src/xnu/libsyscall/mach/mach_init.c:192-193`:
`mach_task_self_ = task_self_trap(); _task_reply_port = mach_reply_port();`), reset on fork
via `_mach_fork_child` (mach_init.c:136). So repeated `mach_task_self()` does NOT round-trip;
only the once-per-init trap does.

The xnu-rpc-free mode is the same idea pushed further: extend "handle it in the guest" from
self-VM to self-ports and self-IPC, and cut the number of per-spawn inits.

## Measured round-trip breakdown (one warm `cider exec true`, Pass 120)

~55 round-trips. Enable with `DSERVER_TRACE_CALLS=1`; ciderd logs each call to
`{prefix}/ciderd.log` (the launcher redirects ciderd stdio there, main.rs:576). Hot calls
(round-trips per spawn):

| call | # | per spawn |
| --- | --- | --- |
| MACH_MSG_OVERWRITE | 38 | 10 |
| MACH_REPLY_PORT | 36 | 8 |
| MACH_PORT_DEALLOCATE | 39 | 5 |
| TASK_SELF_TRAP | 33 | 4 |
| HOST_SELF_TRAP | 34 | 4 |
| THREAD_SELF_TRAP | 35 | 4 |
| UIDGID | 7 | 4 |
| SET_THREAD_HANDLES | 8 | 3 |
| VCHROOT_PATH | 3 | 3 |
| CHECKIN | 1 | 3 |
| FORK_WAIT_FOR_CHILD | 11 | 2 |
| CHECKOUT / KQCHAN_PROC_OPEN / MLDR_PATH / STARTED_SUSPENDED / GET_TRACER | 2/29/10/5/6 | ~1 each |

Two guest nsids participate: the transient shellspawn fork-child and the exec'd image, each
running a near-full init sequence. That doubling is a big part of the count.

## Categorization

- A. Redundant re-init (cut the NUMBER of inits). shellspawn spawns with `fork()`
  (shellspawn.c:281) then `execv()` (:290). The `fork()` runs the FULL atfork child path,
  including `_mach_fork_child` -> `mach_init_doit` -> `task_self_trap` + `mach_reply_port` +
  `mach_driver_init`, and then `execv` immediately discards that image. Those round-trips are
  wasted work.
- B. In-guest-able (the core xnu-rpc-free work). Self-port traps, reply-port alloc/dealloc,
  and port ops on the task's OWN space could be served from a guest-local Mach port
  namespace, exactly as the self-VM ops already are. Needs the guest to own port-name
  allocation and keep ciderd consistent when a name escapes.
- C. Genuinely needs ciderd (irreducible boundary). `mach_msg` to OTHER tasks/services
  (bootstrap, launchd, notifications), the fork/checkin/checkout lifecycle, `task_for_pid`,
  and cross-task port transfer. These define where the daemon stays authoritative.

## Incremental plan (each step independently measurable)

Measure every step with the scratchpad harnesses: `rpc-count.sh` (round-trips per spawn via
DSERVER_TRACE_CALLS) and `agg-ab.sh` / `agg-ab2.sh` (wall-time, cider.orig vs a rebuilt
variant, N sequential `cider exec`). Correctness gate: a known program computes the right
result and exit codes are preserved, over 50x sequential plus a parallel batch.

1. Skip the transient fork's wasted Mach re-init (Category A). VERIFIED: the obvious form,
   switching shellspawn's `fork()+execv()` to `posix_spawn()`, does NOT help.
   `libSystem_posix_spawn_child` (vendor/src/libsystem/init.c:475-491) calls
   `_mach_fork_child()` (line 478) exactly like `libSystem_atfork_child` (line 408); the only
   difference (init.c:440-441) is that the posix_spawn variant skips USER `pthread_atfork`
   handlers, which shellspawn does not register. So `_mach_fork_child` -> `mach_init_doit` ->
   `task_self_trap` + `mach_reply_port` still runs in the transient child and is still discarded
   by the following `execv`.
   THE REAL FIX is a spawn-for-exec path that OMITS `_mach_fork_child` (and any other
   `_*_fork_child` handler that round-trips) in a child that will immediately `execve`, because
   mldr re-inits Mach after exec anyway. The RPC socket the child needs during exec is refreshed
   separately by `sys_fork` (fork.c), not by `_mach_fork_child`, so dropping the Mach re-init is
   plausible. This is a guest-CORE-lib change (libsystem / libsystem_kernel), heavier than a
   shellspawn-only build, and delicate: verify nothing between fork and execve uses
   `mach_task_self_` / `_task_reply_port` / pthread-self, and guard the error/abort path (which
   may `mach_msg` to report failure). Preserve shellspawn's existing fd setup (dup2 of the socket
   fds onto stdio, shellspawn.c:271-277) and its NOTE_EXIT wait.
   CONSEQUENCE: there is NO shellspawn-only bounded quick win. Every xnu-rpc-free step below
   touches a guest core lib or ciderd, so all are supervised, bounded, one-at-a-time builds.

2. Fold per-image setup RPCs into checkin. The checkin reply is currently header-only
   (`rpc_wire.rs` `RpcReplyCheckin`), and each of these per-process RPCs is a separate
   round-trip. By direction (read from their ciderd handlers in handler.rs):
   - SETTERS (guest -> ciderd), fold into the checkin CALL body: `uidgid` (#7, new_uid/new_gid;
     its reply carries the old ids, rarely needed at spawn), `set_thread_handles` (#8,
     pthread_handle + dispatch_qaddr), `vchroot` (#3, a dir fd sent via SCM_RIGHTS, which
     checkin can also carry).
   - GETTERS (ciderd -> guest constants), fold into the checkin REPLY. BIGGEST WIN: the initial
     Mach ports that `mach_init_doit` (mach_init.c:192-193) currently fetches with SEPARATE traps,
     `task_self_trap` (#33), `host_self_trap` (#34), `thread_self_trap` (#35, main thread), and
     the initial `mach_reply_port` (#36). ciderd ASSIGNS these port names at checkin, so it can
     return them in the checkin reply and `mach_init_doit` reads them instead of round-tripping.
     These self-port traps are the largest reducible category in the ~55 (roughly 20 round-trips
     across both nsids). Also fold: `get_tracer` (#6, tracer_nsid), `started_suspended` (#5, a
     bool), `mldr_path` (#10, a path string plus vchroot_len; needs a fixed-max buffer field).
   Collapses the bulk of a per-image init (self-ports + setup constants) into the single checkin. CAVEAT: this is a reorder, so
   each value must be AVAILABLE at checkin time. `set_thread_handles` in particular is set during
   pthread init, which may run after checkin; if so it cannot fold without moving checkin later
   or splitting the set. Verify the guest init order (the libSystem_initializer sequence) before
   committing to a fold set. (Note: task #25 is marked done as "fold init constants into the
   checkin reply", but the current reply is header-only, so treat that as not-yet-landed here.)

3. exec-replacement task/thread swap, unified with the fat checkin. The guest ALREADY flags
   exec: on `execve` it calls `dserver_rpc_checkout(pipe, executing_macho=true)` (execve.c:378)
   and then the re-exec'd mldr re-checks-in under the SAME nsid. ciderd's handlers flag the reuse
   as unfinished (handler.rs:417 "Exec-replacement's task/thread swap is a later refinement",
   :436 "The exec-listener branch is a later refinement"): today it tears the task/thread down on
   checkout and rebuilds on the next checkin. The fix: on a checkout with `executing_macho=true`,
   KEEP the task/thread/ports, and on the same-nsid re-checkin return those SAME port names in the
   (fat, Step 2) checkin reply. Then the re-exec'd image's entire Mach init is a single checkin
   round-trip. This unifies Steps 2 and 3: one fat checkin serves both a fresh spawn and a
   re-exec. Cross-component (ciderd via buck2 + guest mldr/libsyscall), the highest-leverage
   single change after the launcher arc.

4. Guest-local Mach port namespace (Category B, the bulk of the mode). Extend the self-VM
   precedent to ports. Concrete first target: reply ports. Most reply ports are ephemeral
   (allocate, use in one MIG round-trip, deallocate), and the reply-port name already travels
   in the mach_msg header (`msgh_local_port`). So a guest-local reply-port allocator can hand out
   names WITHOUT an RPC; ciderd learns the name lazily when the message arrives and creates the
   port on demand, and deallocate is purely local. Eliminates the `mach_reply_port` (#36) and its
   matching `mach_port_deallocate` (#39) round-trips (order ~13/spawn). Correctness by name-space
   PARTITION: reserve a guest-local range of `mach_port_name_t` (e.g. a high tag bit) so a
   locally minted name can never collide with a ciderd-assigned one, and have ciderd treat an
   inbound name in that range as create-on-first-sight. Generalize the same partition to other
   self-relative port ops. The ESCAPE BOUNDARY (a local name sent to another task, or a right
   transferred cross-task) is where ciderd must still be told synchronously; that boundary is the
   line between xnu-rpc-free and the irreducible Category C.

## Estimated impact (order-of-magnitude, from the Pass 120 counts)

Rough, to size priority, not a promise. Of the ~55 round-trips/spawn:

- Fat checkin (Steps 2 + 3) folds the per-image init handshake: self-ports (~12), initial
  reply_port (part of ~8), uidgid (~4), vchroot (~3), set_thread_handles (~3), mldr_path (~1),
  tracer/suspended (~2). Order ~30 round-trips collapse into the checkins that already happen.
- Skipping the transient fork child's re-init (real Step 1) removes most of one nsid's init on
  top of that.
- Remaining and largely irreducible (Category C): the `mach_msg` service IPC (~10), some
  reply-port churn/dealloc (~5 each), fork_wait/checkout/kqchan lifecycle (~4).

So a plausible target is ~55 -> ~15-20 round-trips, i.e. the ~21ms Mach segment toward
~6-8ms, a warm spawn from ~40ms toward ~25-28ms (~1.5x on top of the banked ~3.5x). Verify
empirically with rpc-count.sh after each step; do not trust this estimate as a result.

## Correctness hazards

- Port-name namespace consistency: if the guest allocates names locally, ciderd must accept
  or relocate them the moment they appear in a `mach_msg` to a ciderd-hosted service. Any
  divergence corrupts IPC silently.
- fork/exec invalidation: any guest-local state must reset exactly where `mach_init_doit`
  resets today (fork child via `_mach_fork_child`, and on exec).
- Signals and psynch: `interrupt_enter/exit` (sigexc) and the psynch ops already have
  bespoke continuation handling in ciderd (the -111 interrupt race, task #44). An in-guest
  port layer must not disturb those paths.

## Notes for whoever picks this up

- Do NOT chase self-port caching: it is already done (mach_init.c). The win is fewer inits
  (steps 1/3) and in-guest self-IPC (step 4), not caching a value that is already cached.
- ciderd has no fast standalone build; it and the guest libs build through buck2 / the
  prefix. Keep builds bounded and one at a time (see the resource note in CLAUDE.md / RTK).
- The launcher (`nix build .#launcher`) IS a fast, light build and is where the already
  banked ~3.5x wins live (1ms poll, persistent container, login home fix).
