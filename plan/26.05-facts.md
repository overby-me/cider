## Masquerade target (Phase A.2)

SDK 14.4 implies a macOS 14.4.x identity:

| Fact | Chosen value |
|---|---|
| ProductVersion / ProductUserVisibleVersion | 14.4.1 |
| ProductBuildVersion | 23E224 |
| Darwin kernel (`kern.osrelease`, `uname -r`) | 23.4.0 |
| `kern.osversion` | 23E224 |
| `kern.osproductversion` | 14.4.1 |

Implemented (2026-07-20):

- `src/frameworks/CoreServices/SystemVersion.plist` → ProductVersion /
  ProductUserVisibleVersion 14.4.1, ProductBuildVersion 23E224,
  iOSSupportVersion 17.4.
- `patches/xnu/0005-masquerade-macos-14.4.1-identity.patch` sets the emulated
  defines in `.../libsystem_kernel/emulation/CMakeLists.txt`:
  `EMULATED_RELEASE=23.4.0`, `EMULATED_OSVERSION=23E224`,
  `EMULATED_OSPRODUCTVERSION=14.4.1`, and the `kern.version` banner
  `Darwin Kernel Version 23.4.0`. These feed the guest-side sysctl handlers in
  `.../emulation/src/xnu_syscall/bsd/helper/misc/sysctl_kern.c`
  (`kern.osrelease`/`osversion`/`osproductversion`); uname(3) follows osrelease.
  The banner keeps upstream's short, semicolon-free form: `add_definitions`
  treats `;` as a CMake list separator, so a full `Darwin Kernel Version 23.4.0:
  <date>; root:xnu-…` string splits mid-argument and breaks the mig codegen
  invocation. The full banner is not needed (no test/consumer parses it; the
  product/build/release values are what matter).
- `CMAKE_OSX_DEPLOYMENT_TARGET` is **intentionally kept at 11.0** (CMakeLists.txt:66).
  Identity reporting is independent of the deployment floor, and raising it to
  14.0 risks breaking Big-Sur-era in-tree submodule sources under the newer
  availability floor (a large, orthogonal rebuild risk). Revisit only if a
  14.0-target build is actually required (per PLAN.md A.2 fallback).

## Milestones reached

- **M0 (2026-07-20): substituted `hello` runs under Darling.** The
  x86_64-darwin `hello` 2.12.3 (`/nix/store/lf0dyrrs…`, substituted from
  cache.nixos.org, a Mach-O `NOUNDEFS|DYLDLINK|TWOLEVEL|PIE`) executes under
  rootless Darling and prints `Hello, world!` (rc 0). Confirms Darling's
  libSystem satisfies a real nixpkgs Darwin binary's imports (the Phase B
  "gap ~0" analysis) with the macOS-14.4.1 identity and no root/setuid.
  Reproduce: `scripts/run-darwin-under-darling.sh <host-store-binary>`.

  Mechanics learned:
  - Host `/nix` is not visible at `/nix` inside the container, but the whole
    host root is mounted at **`/Volumes/SystemRoot`**, so a host store path
    `X` is reachable as `/Volumes/SystemRoot/X`.
  - Rootless runs **one command per fresh container**: a second `darling shell`
    cannot join a running container's mount namespace from a sibling user
    namespace (`/proc/<init>/ns/mnt` open → EPERM), and a fresh prefix's first
    boot races the 15s shellspawn-socket window, so the runner kills any stale
    darlingserver/mldr and retries. This is the main obstacle for the multi-
    invocation guest-Nix installer (Phase 0.5 full / Phase C); see plan/blockers.md.

- **Phase C keystone (2026-07-20): the bootstrap toolchain executes AND
  compiles from source under Darling.** The x86_64-darwin `bootstrap-tools`
  (`/nix/store/v6wk45fap…`) binaries run under rootless Darling: `bash 5.2.37`,
  `sh`, `clang 19.1.7` (auto-target `x86_64-apple-darwin23.4.0`, from our
  identity), coreutils. `clang` then **compiles + links + runs** a C program
  end to end: with `-isysroot <apple-sdk-14.4>/…/MacOSX14.4.sdk` (store path
  `dfd1kij…`, headers under `Platforms/MacOSX.platform/Developer/SDKs/`) it
  produces a Mach-O that executes and prints its output (`clang_rc=0`,
  `run_rc=0`). So the compiler, linker and libSystem all work under Darling;
  M1 (nixpkgs `hello` from source) is a matter of orchestrating the real build,
  not a toolchain gap.

  Environment notes for compiling under Darling:
  - Inside the container `/tmp` and `/private/tmp` are read-only; `$HOME`
    (`/Users/root` when container-root) is writable. clang needs a writable
    `TMPDIR` (set it to a HOME subdir) for its intermediates.
  - The default clang header search is `…/lib/clang/19/include`, `/usr/include`,
    `/System/Library/Frameworks` — none carry the C SDK, so `-isysroot` (the
    apple-sdk) is required, exactly as nixpkgs' cc-wrapper does.

- **M1 (2026-07-20): GNU `hello` builds from source under Darling and runs.**
  `hello-2.12.3` (the nixpkgs `hello.src` tarball) runs `./configure && make`
  end to end inside one rootless `darling shell` session with the bootstrap
  clang + apple-sdk-14.4: `configure_rc=0` (261-line log, no aborts),
  `make_rc=0`, and the freshly linked Mach-O prints `Hello, world!` (rc 0).
  This is the campaign goal's "builds" half; with M0 ("runs") the goal
  (`pkgs.hello` builds **and** runs under Darling) is met at the toolchain
  level. Reproduce: `scripts/build-hello-under-darling.sh`.

  What it took beyond the toolchain (M0/keystone): exactly one syscall fix.
  configure's "whether dup2 works" test aborted the process (`patches/xnu/0006`,
  see plan/syscall-triage.md); with that, configure completed and make/link/run
  all worked first try. Build environment: `CONFIG_SHELL`/`SHELL` forced to the
  bootstrap bash (the host shell path leaks into the container and does not
  exist there), `-isysroot`/`SDKROOT` = the apple-sdk, writable `TMPDIR` in
  `$HOME`, `CC=clang`.

  Follow-ups toward the *official* M1 and the oracle:
  - Phase D oracle: bit-compare the Darling-built `hello` against the
    cache.nixos.org `lf0dyrrs…` output.

- **M1b (2026-07-20): the official nixpkgs `nix` runs and evaluates under
  Darling.** The x86_64-darwin `nix` 2.34.8 (`fw9y98mc…`) loads and runs under
  rootless Darling: `nix --version` -> `nix (Nix) 2.34.8`; `nix eval --expr
  "1 + 2"` -> `3`; `nix eval --expr builtins.currentSystem --impure` ->
  `"x86_64-darwin"` (the A.2 identity flowing through nix). This makes the
  *official* guest-Nix build path (drive `hello` through `nix build` rather than
  hand-run configure/make) viable. Getting here required, in dyld-error order,
  four Darling compat fixes (all committed):
  1. `patches/xnu/0006` — `dup2` to a guarded high fd returns EBADF instead of
     aborting (was also what unblocked GNU hello's `./configure`).
  2. `patches/libcxx/0001` — build C++17 `<filesystem>` into libc++ (was 0
     symbols; libnixutil needs 26).
  3. `src/frameworks/Network/src/nw_stubs.c` — 39 logging `nw_*` stubs for
     libaws-c-io (nix's S3 backend; never called for a local build).
  4. `patches/libcxx/0001` — a self-contained C++17 `std::pmr`
     (memory_resource + get_default_resource + monotonic_buffer_resource ported
     from LLVM-17 libcxx, matching macOS-14's ABI). `std::pmr` landed in libc++
     at LLVM 16; Darling's is LLVM 13, so it lacked it entirely.

  Mechanics: run `nix` with `/nix -> /Volumes/SystemRoot/nix` (host store) so
  its absolute store-path deps resolve.

  `nix build` reached but not yet completed — the build machinery runs (nix
  instantiates the `.drv` and decides to build a trivial derivation) but hits
  two concrete limits:
  - **`error: building using a diverted store is not supported on this
    platform`** with `--store <prefix>/ns`. Builds must use the *native*
    `/nix/store`. But `/nix` is the SystemRoot symlink to the root-owned,
    read-only host store, and nix's own libraries also live there, so it can't
    simply be repointed to a writable local dir (nix wouldn't find its own
    libs). The clean fix is a proper **in-prefix nix install**: a writable
    `/nix` inside the Darling prefix holding nix + its closure (and the build
    deps), i.e. the `scripts/install-nix-in-darling.sh` workflow (single-user),
    run in one darling session (the one-command-per-container limit).
  - **Guest DNS: `getaddrinfo` is broken under Darling.** nix's libcurl uses
    `getaddrinfo` and fails with `Could not resolve host`, while the
    bootstrap-tools `curl` (its own resolver: reads resolv.conf and queries the
    nameserver over UDP directly) *does* resolve (it reaches a TLS/CA error, so
    UDP DNS to `8.8.8.8` works and the container's `/etc/resolv.conf` is fine).
    So the gap is specifically Darling's `getaddrinfo`/libinfo DNS path, not
    sockets or certs. Fix options: implement/repair Darling `getaddrinfo`, an
    `/etc/hosts` workaround, or pre-populate the store (no substitution needed);
    for TLS also set `NIX_SSL_CERT_FILE` to a cacert bundle.
  - **Writable native `/nix` needs a container-level mount.** An overlay at
    `/nix/store` (host store lower + writable upper) would give a writable native
    store, but it cannot be done from inside `darling shell`: the Darwin userland
    has no `mount` and Linux overlayfs is not a macOS concept. It must be set up
    at the **Linux level in Darling's container bring-up** (darlingserver / the
    launcher adding an overlay or bind mount for `/nix`), plus `sandbox = false`.

  Net: the official `nix build …#hello` (C.3) needs three Darling-internals
  pieces (each a real sub-project): `getaddrinfo` DNS (or a pre-populated store),
  a container-level writable `/nix` overlay, and sandbox-off builds. The campaign
  goal itself is already met via the bootstrap toolchain (M1); guest `nix` runs +
  evaluates (M1b).
